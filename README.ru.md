# agent-kit

Плагин для Claude Code. Вы один раз описываете проект, дальше команды строят по этому описанию.

Описание лежит в `docs/knowledge/`, по файлу на слот: что продукт делает и чего сознательно не
делает, акторы, сущности и их состояния, действия, экраны, интеграции, сценарии, стек — и то, что
входит в первую версию. Пишет его `blueprint`. Читают и превращают в код `ship`, `fix`,
`sprint` и `mvp`. Сверяет код с описанием `audit`.

## Установка

```text
/plugin marketplace add IliaSadovskii/agent-kit
/plugin install agent-kit@agent-kit
```

На весь репозиторий — в `.claude/settings.json`:

```json
{
  "extraKnownMarketplaces": {
    "agent-kit": { "source": { "source": "github", "repo": "IliaSadovskii/agent-kit" } }
  },
  "enabledPlugins": { "agent-kit@agent-kit": true }
}
```

Нужны `git` и `python3`, для пул-реквестов ещё `gh`. Остальным пяти командам этого хватает;
`sprint` и `mvp` требуют ещё `tmux` — они дают каждой фиче свою живую сессию.

Эти две идут ночь или сутки и пережидают лимиты аккаунта сном до сброса, поэтому им нужна машина,
которая тоже не засыпает, — подойдёт любой сервер. Если возиться с настройкой не хочется,
[agent-vps](https://github.com/IliaSadovskii/agent-vps) — сервер, уже собранный под это: сессии
переживают перезагрузки и доступны из мобильного приложения. Киту он не нужен и он о нём не знает.

## Команды

### `blueprint`

Опрашивает вас и пишет описание. Каждый слот коммитится по готовности, так что можно остановиться и
вернуться позже.

- `blueprint` — продолжить с пустого, устаревшего или помеченного прошлым прогоном
- `blueprint "переработать карту"` — добавить или переосмыслить одну вещь
- `blueprint --check` — где стоит проект: построено, запланировано, открытые вопросы, допущения,
  которые ждут вашего ответа

На готовом коде сначала читает код и приносит черновик на исправление. Приложение не запускает, ваши
документы не переписывает — ссылается на них.

### `ship <ключ действия | что построить>`

Одна фича, один пул-реквест. Проектирует по записи, собирает, тестирует, ревьюит, открывает PR.

Спрашивает только про развилки, которые дорого откатывать: форма хранимых данных, публичные
контракты, права, деньги. Тесты берутся из записи и пишутся до кода. В PR перечислено, что принято
допущением и что доказано.

Работает и без blueprint — от текста задачи.

### `fix <что не так>` · `fix --pr <n>`

Небольшая правка: ваше описание, замеченный сбой или круг комментариев к PR. Сначала находится
причина, потом доказывается тестом, который падает до правки и проходит после, — и правку один раз
откатывают, чтобы увидеть, как тест падает снова. Меняется наименьшее, что делает тест зелёным;
уборка по соседству уходит в список долга.

### `sprint <тема>`

Несколько фич, отбрифованных за один заход, дальше собираются без вас — каждая своей видимой
сессией, по очереди, цепочкой, и вся пачка приходит одним мержабельным пул-реквестом. Рядом стоит
управляющая сессия: расскажет, как идут дела, и примет *пропуск* и *стоп*.

### `mvp`

Всё, что входит в границы MVP: строится, пока никто не смотрит, потом аудит, потом сценарии на
запущенном приложении — и один pull request, который можно открыть и потыкать.

Задаёт один вопрос, в самом начале: этот объём или уже, с ценой каждого варианта. Дальше идёт
партиями примерно по пять фич, и после каждой партии pull request рассказывает, что уже работает.
Своей логики сборки у неё нет: она собирает партии, а строят те же драйвер, `ship` и закрывающий
сеанс.

### `next`

Для сессии, открытой после перерыва: где стоит проект, что мешает и какую одну команду запустить —
с причиной. Читает ветки, пул-реквесты и их сборку, брошенные на полпути прогоны, долг и аудиты;
не меняет ничего, кроме бухгалтерии, которую только что проверила.

### `audit [линза] [область]`

Сверяет существующий код с тем, что описание объявляет верным, и пишет список работ.
Ничего не меняет.

| Линза | Что проверяет |
|---|---|
| `tests` | что код обещает, а тестами не проверено — и где тест есть, но проверяет не то |
| `deps` | какие пакеты устарели или дырявые, и опасно ли это конкретно здесь |
| `scenarios` | проходит ли пользователь весь путь до конца и на каком шаге он ломается |
| `security` | кто может увидеть или сделать то, чего не должен |
| `performance` | где код тормозит по понятной причине: лишние запросы, выборки без границ, работа в цикле |
| `conventions` | где код разошёлся с правилами, которые вы сами для него написали |

- `audit` — все линзы, от дешёвых к дорогим
- `audit тесты` — одна линза; `тесты` и `tests` это одно и то же
- `audit тесты модерация` — суженная областью
- `audit "почему модерация тормозит"` — скажет, какую линзу понял, и запустит

Любой прогон заодно ищет в коде поверхности, которых нет в описании, и наоборот. У каждой находки
стоит файл и строка, которые её доказывают, — вердикт проверяется за десять секунд. Список лежит
в `docs/audits/<линза>.md`, разбит на партии по одному прогону `ship`; помеченный отклонённым пункт
следующие прогоны не поднимают.

## Порядок работы

| Что есть | Порядок |
|---|---|
| только идея | `blueprint` → `mvp` → `sprint` |
| полукаркас | `blueprint` → `audit` → `ship` / `sprint` |
| готовое приложение | `blueprint` → `audit` → `sprint` → `fix` |
| непонятно, на чём остановились | `next` |

`audit` нужен там, где за написанием кода никто не следил: доставшийся проект или батч, приехавший
за ночь. После `ship` он лишний.

`ship`, `fix` и `sprint` работают вообще без blueprint, от текста задачи: первая команда в проекте
не должна начинаться с часового интервью. `mvp` без него не запустится — границы и есть то, что
говорит ему, когда остановиться. `audit` тоже требует описания, кроме одной линзы: у `deps`
эталон — реестры пакетов, и описание ей не нужно. А `next` запустится, но ранжировать ему будет
нечего, и он просто скажет написать blueprint.

## Файлы

| Путь | Что | В гите |
|---|---|---|
| `docs/knowledge/` | описание, по файлу на слот | да |
| `.agent-kit/project.yml` | язык, команды проекта, вердикт по каждому слоту | да |
| `.agent-kit/runs/<slug>/` | состояние прогона и лог событий | нет |

Кит работает на ветках и никогда не мержит пул-реквесты — и с версии 1.0.0 это машина, а не
инструкция: пока прогон идёт, хук вне контекста модели отказывает в мерже, в force-push и в push
в основную ветку. Ваши собственные сессии с ним не встречаются.

## Разработка кита

`scripts/validate.sh` проверяет раскладку, манифесты, версии, внутренние ссылки, форму файла
прогона, разметку самого плагина, регистрацию хука и то, что оба README описывают ровно те команды,
которые поставляются; CI гоняет его же.
`scripts/measure.py <проект>` считает стоимость прогонов — по сессиям или по веткам. Дизайн —
в [docs/design/](docs/design/), релизы — в [CHANGELOG.md](CHANGELOG.md).
