# S5 — the bench

Written before building it, 22 August 2026, so that the next session starts from decisions
rather than from a blank page. S0–S4 are done: the package, the state, the step contract,
Claude Code at level B, and one feature end to end — three of them, delivered to
`kit-sandbox` as pull requests 1, 2 and 3.

The plan's own words: *A sample repository with planted traps and judges that are scripts.
Done when one command reports which mechanisms fired and which did not. Why here: before S4
there is nothing to judge; after S4 every further change needs judging, and a live night can
no longer answer for it.*

---

## Why this is the next thing, and not something more interesting

S4 ended with two reviewers and nineteen findings. Fourteen fixes went in, judged by 299
tests and three features built in a friendly sandbox. **Eight of the nineteen were proved
only by running the kit against something hostile**, and one of those eight was found by
accident on the third live run, because a branch happened to be occupied.

That is the whole argument. The tests are a clean room; a live night is one sample of a
friendly world; two reviewers cost an afternoon and do not repeat. The bench is the third
thing: the same run, but with the branch occupied, the tree dirty, `gh` unauthenticated
and the suite red **on purpose**, and with scripts saying which mechanism fired.

## The trap list is already written

The eight defects S4's review proved are the first eight cases, and they are not invented —
each one already has a reproduction. In rough order of what they cost:

| Trap | The mechanism it must fire |
|---|---|
| the branch already exists and holds somebody's commit | delivery refuses **before** touching it |
| the branch exists and holds nothing | delivery uses it rather than stranding the feature |
| a `.env` and a log beside the changed files | only what `build.files` names is committed |
| the build names a file it never wrote | delivery refuses, and nothing is committed |
| `gh` fails after the commit | running it again carries on rather than starting over |
| a command that hangs and spawns a child | the child dies with it |
| a build that says `complete: false` twice, then finishes | every part reaches review and delivery |
| a review whose `verdict` and findings disagree | delivery refuses as a disagreement |

Then the ones S4 built and only ever saw succeed:

| Trap | The mechanism it must fire |
|---|---|
| a blocking finding | delivery refuses, the run **stops** rather than fails, exit code 5 |
| a red test command | the gate closes, the step still records `passed` |
| a design with no `verification` | the step is refused and the reason names the field |
| an assumption with no `expensive` | the step is refused and the reason names the field |
| a step that never finishes | the run stops after the declared number of continuations |
| a project that declares no commands | `verify` refuses with `no-commands` |

**A trap is not a test of the kit's Python. It is a run of the kit** — through the driver,
against a real repository, with the fake provider answering from a script. That is what
makes it able to catch what unit tests cannot.

## The shape

`bench/cases/<name>/` holds what a case is:

- `case.toml` — what this case plants and what must fire: the expected outcome (a run that
  is `done`, `stopped` or `failed`), the expected refusal code, the exit code.
- `repo/` — the sample project, or a script that makes one. A case that needs a git remote
  makes a bare one beside it; nothing reaches the network.
- `replies/` — what the fake provider answers, one file per attempt. Every case that does
  not name a real provider uses `providers/fake/`, and therefore costs nothing.

`agent-kit bench run [--case NAME]` prints one line per case — fired, did not fire, or
could not be judged — and exits non-zero if anything did not fire.

**A judge is a script, not a model.** It reads the run's own state and the step directories,
which is exactly what the kit already writes: `run.json`, `steps/<n>-<name>/output.json`,
`refusal.txt`, `meta.json`. Nothing new has to be recorded for the bench to work — if a
judge cannot see something, that is a finding about the kit, not about the bench.

## What the sandbox is, settled 22 August

**`kit-sandbox` is a fixture, not a project the kit develops.** Its `main` is the baseline
every version of the kit starts from, and it stays on its first commit. Nothing the kit
delivers there is ever merged, and after a live run the branches it made are removed.

The reason is the one the plan already gives for the bench existing at all: *with more than
one provider, "checked by a live overnight run" stops working — a bad model and a bad night
become indistinguishable.* A moving baseline does the same damage from the other side. If
`main` advances between runs, a worse kit against an easier starting point and a better kit
against a harder one look identical, and the comparison the sandbox exists to support is
gone.

This was nearly decided the other way, and the argument for merging is worth keeping because
the need behind it is real: **a kit that only ever builds against a pristine thirty-line
`Money` never builds on top of its own earlier work** — a grown test file, a second feature
touching the first, a house style that is its own. That is a genuine gap in coverage, and
merging is the wrong way to close it, because it buys the coverage with the baseline.

The right way is a case:

| Trap | The mechanism it must fire |
|---|---|
| a repository that already holds a feature the kit built, and a brief that touches it | the design names the seam to the existing code; the build does not rewrite it; the commit holds only the new work |

Built fresh, judged, thrown away, like every other case. The coverage without the cost.

**The two roles, kept apart.** The sandbox is the live check that the kit works against a
real GitHub, a real `gh` and a real network — realism, no determinism required. The bench is
the instrument that compares one version against the next — determinism by construction,
because each case makes its repository and destroys it. Asking the sandbox to be both is
what produced the merge recommendation.

## What is open, and needs deciding on the way

**Open question 11 — what the bench may spend.** The plan: *a declared ceiling per bench
run, and cases marked cheap or full — the cheap set on every change, the full set before a
release.* Proposal to build: every case above is `cheap` and uses the fake provider, so the
whole set costs nothing and runs on every change. `full` cases, which drive a real provider,
wait until there is a second adapter to compare against — S9. Say so out loud rather than
building a ceiling nothing yet needs.

**A case must not touch the machine it runs on.** Each one gets a temporary directory, its
own `HOME`, its own bare remote, and a `gh` on `PATH` that is a script. The suite's own
`conftest.py` already does the `HOME` half and is the pattern to copy.

`agent-kit bench run` reports every case above as fired, and breaking any one mechanism by
hand makes exactly one case say it did not.

# S6, which comes after, and the question that must be answered first

**S6 · The knowledge, through the program.** The model returns fields, the driver writes the
file and the mark. *Done when a feature cannot be closed while an expensive assumption has
no block, and the bench has a trap proving it* — so S6's own condition names the bench,
which is why it is second and not first.

What S6 has to build: a `knowledge/` module that reads and writes a project's
`docs/knowledge/`, the join the second version never made (an expensive assumption owes an
`[assumed …]` block), and the marks a run leaves behind. The fields for it are deliberately
not written yet — S4 wrote `assumptions` with `expensive` answered, and that is the half
that has a reader today.

**The question for the owner, and it blocks S6, not S5:** *what is the knowledge format in
the third version?* Three answers are possible and they are not equivalent:

1. **What the second version wrote, unchanged**, so `beeplish` carries across as it is and
   `agent-kit init` migrates nothing.
2. **A format of the kit's own**, with `init` reading `docs/knowledge/` and migrating — this
   is what the plan's open question 10 said and what S4 deliberately did not build.
3. **Nothing inherited**: the third version starts a project's knowledge fresh, and the
   second version's stays where it is until somebody moves it by hand.

Whichever it is, it decides what `init` does, what `knowledge/` reads, and whether the
sandbox is a fair place to test S6 at all — it has no knowledge in it. **Ask this before
starting S6; do not choose it while building.**

## Should S5 and S6 be one session?

No, and the reason is the question above rather than the size. S5 is a full session of
work: fourteen cases, a runner, a judge, and each case has to be built to fail first. S6
cannot honestly start until the format is decided, and a session that decides it while
building is the thing this project spent S4 learning not to do.

Do S5. If it lands green with room to spare, put the question to the owner and stop there.

# What was built, 22 August 2026

`agent-kit bench run` — fourteen cases, all of them firing, in twenty seconds and
for nothing. `make bench` is the same thing from outside the container. The suite
is 320 tests.

## What a case turned out to be

```
bench/cases/<name>/
  case.toml     what this plants and what must fire
  repo/         files laid over the baseline project before its first commit
  plant.sh      run in the repository afterwards, to put the trap in place
  replies/      what the fake provider answers, one file per attempt, in name
                order; a `.sh` of the same name is what that session did
  judge.sh      reads the run and says whether the mechanism fired
```

Everything but `case.toml` is optional, and half the cases need only replies. The
declaration holds what every case shares — the exit code, the run's status, a
substring of the reason it recorded, the status each step ended on — and
`judge.sh` holds what only that case can say: that a branch tip is untouched,
that a commit holds one file and not three, that a child stopped growing a file
when its parent was killed.

**A judge's exit code means one of three things,** and the third is not a third
kind of failure: `0` the mechanism fired, `1` it did not, anything else the judge
itself broke and nothing was judged. A case that cannot be read, a world that
cannot be made and a run that left no state land in the same third column. The
bench exits `6` if anything is not in the first.

**The world is made and destroyed per case:** a temporary directory with its own
`HOME`, its own `XDG_*`, its own git identity through `GIT_CONFIG_GLOBAL`, a bare
remote a directory away, and a `gh` on `PATH` that is a shell script. Nothing
reaches the network. A case that fires is deleted; one that does not is kept when
`--keep DIR` says where, and the line says where it was left.

**The kit is run as a command, not imported** — `run new`, then `run go
--provider fake` — so the exit code a judge reads is the one a script would have
read.

## Three things the kit had to learn, and each is a defect the bench found

1. **A project says how long it waits for its own command.** `command_timeout` in
   `project.toml`, read by `verify`. Without it a planted hang costs the bench an
   hour, and the kit's hour was a constant nobody could answer for. A project
   knows whether its suite is seconds or half an hour; the kit does not.
2. **A run that `stopped` exits 5, whichever step said so.** A closing gate
   already did. A step refused for a reason the method expects — a blocking
   finding, a build that never finished — stopped the run and exited 3, which is
   the code for a kit that could not do its work. A script could not tell the two
   apart, and telling them apart is the whole point of the code.
3. **The fixture provider acts as well as answers.** A session does two things,
   and one that only answers cannot plant a trap: the build it plays says it
   wrote a file and no file was written. A reply may now carry a script of its
   own name beside it, run in the project before the answer is given.

## The condition, and how it was checked

*`agent-kit bench run` reports every case as fired, and breaking any one
mechanism by hand makes exactly one case say it did not.*

Five mechanisms were broken by hand, one at a time, and each pointed at one case
and no others:

| What was broken | What said so |
|---|---|
| the branch guard, made to say nobody's branch holds work | `branch-holds-somebody-else` |
| `git add -A` instead of the files the build named | `a-dot-env-beside-the-work` |
| the verdict no longer has to agree with its findings | `a-review-that-disagrees-with-itself` |
| a split step keeps only its last session | `a-build-in-three-sessions` |
| a timed-out command no longer takes its group | `a-command-that-hangs` |

Each break was reverted before the next. The wording of what did not fire is the
part worth keeping: *"the commit holds more than the build named: .env; money.py;
scratch.log"* and *"the child outlived the command it belonged to"* say what
happened, not that an assertion failed.

## Open question 11, answered as proposed

**Every case is cheap and there is no ceiling.** All fourteen answer from
`providers/fake/`, so the whole set costs nothing and runs on every change. There
is no `cost` field in `case.toml`, because nothing would read one: a field with
no reader is not written. `full` cases — the ones that drive a real provider —
arrive with S9, when there is a second adapter to compare against, and the field
arrives with them.

## What was decided while building, and is worth saying out loud

**One case plants the aftermath rather than producing it.** The trap *gh fails
after the commit; running it again carries on* cannot be produced by two runs of
the kit, because a failed run does not resume — that is deliberate, and the
answer to it is a `retry` command that is not built. So the case plants what the
failed delivery left behind: the commit on the branch, pushed, the working copy
on the branch and clean, and no pull request. The mechanism it fires is the same
one, and the case is honest about which half it planted.

**The seam case is not built.** The note above proposes a case for *a repository
that already holds a feature the kit built, and a brief that touches it*. Against
a provider that answers from a file, "the design names the seam" is a tautology:
the file names it because it was written to. It is the first `full` case and it
waits for a real provider, which is S9.

**`bench/cases/` is not in the wheel.** The bench is the instrument that compares
one version of the kit against the next, and it is run from a checkout. A tool
installed with `uv tool install` has no cases and says so by name (`no-cases`)
rather than reporting an empty suite that passed.
