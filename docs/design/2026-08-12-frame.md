# The frame child, a chain that is not a dependency, and one honest test

Written 2026-08-12, out of a session that set out to ask what the kit's architecture looks like from
outside it. Three things came back worth acting on; two of them turned out to be one mechanism.
All three are in 2.7.0.

## What was wrong

**Nobody designed across features.** `blueprint` settles *what* a feature does. `ship` settles *how,
in this codebase* — and sees one feature. The brief sees the whole batch and is told, correctly, not
to design: it reads little code, and the child will have read more of it within the hour. So the
decisions that live *between* features — the shared table, the layer both of them reach through, the
place a thing lives — were taken five times independently, by five sessions that could not see each
other. `sprint`'s own text names the symptom ("two features write to the same table") and gives the
brief nothing to do about it.

**And one failure took the whole night.** Every child named the one before it as `parent`, "whether
or not this feature depends on it", and the driver skipped the descendants of anything that failed.
Measured against how children actually fail — `orchestrate.py` writes `blocked` when a session ends
without reaching a terminal step — the common cause is a session that died, stalled or hit a limit.
That has nothing to do with the feature, and it cost up to N−1 features a night.

## Why the frame writes prose and not code

The first design had the frame child build the shared scaffold in code: migrations, base types, the
common seam. The argument against it is the stronger one and it is the owner's: **the features do not
exist yet.** Anything built for them in advance is built against a guess, and the guess is checked
for the first time by the third feature, which then either fits itself to something wrong or breaks
it for the two before it. The risk is not symmetrical — a bad *rule* the next run reads past or
bends; bad *code* it is standing on.

So the frame child writes no product code. What it produces is agreements, and they live where the
kit already has a reader for them.

## Why `stack.md` and not a document of its own

A new `architecture.md` would have no obliged reader. Anthropic's own guidance warns that a
referenced file may go unread, and this kit already refused to split `blueprint`'s interview for
that reason.

`stack.md` is the opposite of that, on three counts:

- `check.py --brief` prints it **whole** to every `ship`, so it arrives in the one call a feature
  makes before it designs. Nothing has to remember to open it.
- `ship` is already told to stay inside the stances it records.
- `agent-kit:reviewer` already judges a diff against it. A frame line written so that a diff can be
  held to it therefore brings its own enforcement, and one written as a slogan brings none. That is
  why *checkable against a diff* is the first rule in `references/frame.md` and why "we use DDD" is
  the example of what does not count.

The block also inherits a closer, which is the third of the four answers this kit demands: it is
folded into the decisions per area by `blueprint`, **after the batch has merged** — because only
then is there code to read it against, and what the features departed from is a fact rather than a
plan.

It is reported by the check as a statement, not a finding. Every batch leaves one, and a finding
raised on each would have every command after every sprint report the knowledge as broken — the same
mistake `[stale …]` and `[accepted …]` already avoid, for the same reason.

## The chain and the dependency are two different questions

This is the whole of the second half, and separating them is what makes it safe:

- **the chain** — what a feature is built *on top of*. Always everything built so far. It is what
  makes integration a property of the batch rather than a step at the end, and it is unchanged.
- **`needs`** — what a feature cannot be built *without*. Usually much less, often nothing.

Only the second decides skipping. `base` and `parent` now point at the last child actually built,
not at the previous one in the list, so a blocked feature no longer leaves the ones behind it
branching off a branch that was never pushed.

**A missing `needs` is not `[]`.** Absent means nobody looked, and the driver falls back to the
feature before it in the queue — which is exactly what a chained batch has meant since it was
written. Reading the two the same way would silently turn every batch composed before today into a
batch of independents. `[]` means somebody looked and there are none. This is the kit's own rule
about a check that cannot read its input, applied to a field.

The ordering is arithmetic, so it is in the program: the driver takes the frame child's map, writes
each `needs`, and re-sorts `children` with a stable topological sort — stable because the composing
order is meaningful and is the tie-break, not something to recompute. A cycle is not resolved by
picking a winner: the queue is left as written and the features caught in it are named in the
batch's `blockers`, which the closing session puts in the pull request.

## What an independent read of this change found

Two passes that had taken no part in the reasoning were asked to break it, one over the programs and
one over the mechanisms. Nine of their findings were acted on before this shipped; four are worth
recording, because each is a rule this kit already had and this change had quietly broken.

- **The batch opened with its own most fragile link.** A frame child whose session died would land
  in the driver's skip set, and every feature behind it would be skipped as needing it — the exact
  failure this release exists to end, reintroduced by the mechanism meant to end it. Reproduced,
  then fixed where it belongs: a child carrying its own `prompt` is not a feature, nothing is built
  on it, so its failure cascades to nobody. That covers the audit child of an `epic` too.
- **Every batch would have closed with two defects that were not defects.** The frame child carries
  `command: "ship"`, so `run_defects` asked it for a suite it has no reason to run and a mutation
  count it has no code to produce — into `blockers`, into the pull request, every night. Both rules
  now skip an errand.
- **The fallback was not the old behaviour it claimed to be.** *The feature before it in the queue*
  and *the `parent` the composing session wrote* are the same thing in an ordinary batch and differ
  in three real shapes — a batch of independents with `parent: null`, an audit child sitting between
  two features, a slug in the queue with no run file. The driver now snapshots the authored `parent`
  before it rewrites any of them, which is the claim the migration note makes.
- **`why` was a cheap path out of the whole mutation mechanism.** Not running the tool and writing
  *it would not start* satisfied the check and read like a result. It now counts only with the
  command that was actually run beside it — the smallest artefact that path does not produce for
  free, which is the same move the kit made for the audit lenses' citations.

Two more of the same family were closed in the frame instruction itself: every line of the block now
cites a path or symbol that exists today, and `notes` names the files that were opened. Without
those, *nothing to say* — which the instruction explicitly blesses as a result — is indistinguishable
from *nobody looked*, and it is the cheapest output the step can produce.

## What this costs, and the new risk

One session per batch, and it is skipped for a batch of two.

The risk is new and worth stating plainly: **the accuracy of `needs` now affects correctness, not
just speed.** Before, everything chained, so a missed dependency was impossible. Now a feature the
frame child wrongly called independent can be built without ground it needed. Two things stand
against it — the instruction says doubt goes to the dependency, and the last child still runs the
whole suite on the tip of the chain, so a real divergence surfaces there rather than in production.

## The third one: a test that was never seen red

`ship` has said *write the test before the code* since it was written, and nothing in the kit has
ever produced evidence that it happened. Everything the pipeline knows about a test is the word of
the session that wrote it — that it came first, that it covers this line of the entry. The cheap
path is not laziness and it is not rare: write the test after the code, against what the code
already does, and it passes for ever, asserts nothing, and is indistinguishable from a real one in
the diff, in the coverage, and to the reviewer.

This is the kit's oldest lesson — name the cheapest way to produce plausible output, then demand an
artefact that path cannot produce — applied to the one step that had no artefact at all. The outside
work says the same: 2026 papers on coding agents report that agent-written suites reach high
coverage while killing far fewer mutants, and that the gap between visible and held-out tests grows
with task complexity.

Two mechanisms were considered and one taken.

**Rejected: the agent breaks a line and reports what happened.** It is the same word from the same
session one level down. A run that would write a test after the code will report a red run it did
not have, and nothing distinguishes that either.

**Taken: a program does it.** `commands.mutate` in `project.yml`, run by `ship` after the suite, its
two numbers copied into `mutation`. The owner's objection to inventing it — that the kit cannot know
the stack, and deleting a random line yields a syntax error rather than a behavioural one — is
exactly why nothing here is invented: mutation testing is decades old, every major ecosystem has a
tool for it, and those tools work on the syntax tree with operators that keep the code valid (`>`
for `>=`, `==` for `!=`, dropping a condition). The kit declares a slot and names the tools; the
project fills it.

Three properties matter more than the mechanism:

- **Bounded to the changed files.** A whole-project run re-runs the suite once per mutation. An
  hour-long step is a step every night skips.
- **A survivor is a finding, never a blocker.** Some mutations change nothing observable, and there
  is no honest threshold to fail a run against. The numbers go in the pull request, and a survivor
  sitting on a line of the entry is worth a test before the run goes on.
- **No command is an answer, not silence.** `check.py` asks for the field only where the project
  declared a way to fill it, and refuses a finished run that left it empty when it did — because a
  run that skipped the step and a run that passed it must not read alike.

## What was considered and not done

- **Best-of-N on the design step.** Three approaches judged, for the expensive fork only. Cheap
  relative to a feature and aimed at the most consequential decision a run takes. Not now: it is a
  change to `ship`, and this release changes the batch.
- **One session per task instead of per feature.** The handoff mechanism already cuts a session when
  it has grown; cutting it *before* it grows may be cheaper still. It is a measurement, not an
  argument, and it belongs on a live project.
- **A record of what the kit itself costs and produces.** `spent` counts hours, features and
  sessions. Findings per feature, blocked runs and their causes, the debt curve — none of it is
  collected, so "did 2.6.0 help" is answered by impression.
- **Anything that reaches outside the repository.** Runtime errors, telemetry, whether a shipped
  feature is used. The loop is closed on itself and cannot learn that a description was wrong about
  the world rather than about the code. Deliberately left.
