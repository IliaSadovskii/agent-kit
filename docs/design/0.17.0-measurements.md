# What 0.17.0 cost, and where it broke

Measured 2026-07-31, after a run of the 0.17.0 pipeline was stopped and rolled back. Kept because
the v1 rewrite is argued from these numbers rather than from impressions, and because two of the
obvious hypotheses turned out to be wrong. Nothing here describes the current kit.

## What 0.17.0 changed

A feature runs as four short sessions — `ship --stage design|build|review|deliver` — driven by
`sprint`, with `handoff.yml` carrying branch, base, plan path and suite result between them. Model
tiers per stage (design/review opus, build/deliver sonnet). One review wave over a frozen diff
instead of three serial passes. PRs open ready and are converted to draft by `deliver`.
`sprint-watchdog.sh` resumes the sprint when the driving session dies.

## What it actually cost

Method: sum `cache_read_input_tokens` over every transcript, deduplicated by `message.id` (the
transcript repeats `usage` once per content block — without dedup everything reads ~1.7× too high),
including `<session>/subagents/*.jsonl`.

| | night run, 0.16.0 (one session per feature) | 0.17.0 (four stages per feature) |
|---|---|---|
| features | 21.7 / 16.5 / 62.4 / 61.5M | 01 — 19.9M (complete)<br>02 — 23.1M (complete) |
| orchestrator | 34.8M | 3.9M |
| per feature incl. orchestrator share | **49.2M** | **~27M** |

Feature 01 by stage: design 1.1M, build 5.0M, deliver 0.8M, **review 13.0M** — of which 8.4M is
subagents. The review wave alone costs more than design, build and deliver together.

Inside that wave, on a markdown-only diff:

| pass | cost | findings |
|---|---|---|
| `code-review` plugin fan (5 reviewers + 6 confidence scorers) | **6.7M** | 2 |
| `agent-kit:reviewer` | **0.66M** | 2 major + 10 minor |

## Assumptions that proved wrong

- **"Staging halves the cost."** Half true, and not for the expected reason. Per-feature cost did
  fall, but the reliable part of the win is the orchestrator dropping 9× (34.8M → 3.9M) because
  orientation moved to a file. The night run's four features ranged 16.5–62.4M, so feature-to-feature
  comparison is too noisy to claim more.
- **"The `code-review` fan is silently running on opus."** False. It runs Sonnet reviewers and
  Haiku scorers exactly as its command specifies. The cost is volume — five agents each
  re-exploring the repository from nothing — not tier. Nothing is saved by routing it differently.
- **"Verification is ~70% of a feature."** This one held, and staging did not touch it. It is now
  the whole remaining problem.

## Problems in 0.17.0

**P1 — the watchdog sleeps for a day on a stale rate-limit notice.** `until_reset` reads
`resume.log`, which is never truncated. After the named hour passes, the same line is re-read, the
hour reads as already-past, `+86400` fires, and the watchdog logs `sleeping 86100s`. Observed live.
Fix: consume the notice once, and cap the wait (no limit window exceeds a few hours).

**P2 — liveness is measured by a file written only at the end.** A stage's `claude -p` output is
appended to `run.log` when it exits, so any stage longer than `WATCHDOG_WORKING` (20 min) looks
dead. The watchdog would then start a second orchestrator on top of a live one. This never fired
only because the watchdog blocks inside its own resume call and stops ticking. The signal that does
survive a long stage is the session transcript, whose id the orchestrator writes to `queue.yml`
before launching.

**P3 — every resume starts a new orchestrator.** No stable session id is recorded, so the sprint
appears as a chain of unrelated headless sessions and cannot be opened or followed in the app.
Recording the orchestrator's id beside the queue (not in it — the orchestrator rewrites the queue
and does not know the field) and resuming that session fixes it, at the cost of carrying context.

**P4 — `stop-guard.py` keys on the branch, not the session.** Any conversation in this repository
while a feature branch is checked out is treated as that feature's pipeline and blocked at Stop,
demanding it settle steps it never ran. This happened to a plain analysis session today. Writing a
false `skipped` line to satisfy the guard would make the real stage skip its own review, so there
is no safe workaround. Feature `04-step-gate` is the design that fixes it: key run state by session
id.

**P5 — the orchestrator leaves the repository on a feature branch when it dies**, which is what
turns P4 from theoretical into routine.

**P6 — three process levels make progress unobservable.** watchdog → orchestrator → stage, all
headless. Answering "is it still working?" required reading `ps`, transcript mtimes and log files.
This is the complaint that stopped the run, and it is a property of the architecture, not a bug.

## Options considered, none decided

1. Run the `code-review` fan once on the integration PR instead of per feature. Saves roughly 40M
   across a seven-feature sprint — more than staging saved. Cost: findings arrive at the end, and
   fixing them touches several branches of the stack.
2. Skip the fan entirely on diffs with no executable surface. The kit already suggests narrowing
   the wave by diff; it does not make it a rule.
3. Drop the orchestrator level — the watchdog launches stages from `queue.yml` directly. Two levels
   instead of three. Cost: judgement calls (retry vs. block) move into a shell script.
4. Drop the unattended run altogether. One feature, one visible session. Everything in P1–P3 and
   P6 exists only to cover the case where nobody is watching.
5. Lower the `review` stage's own tier to sonnet — its 4.6M is orchestration and fixing, not
   reviewing, and the fix diff is re-reviewed anyway.
