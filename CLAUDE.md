# agent-kit — the third version

A console application for Linux that drives other people's CLI agents. The plan it is
built from is `docs/design/2026-08-22-the-third-kit.md`; read that before changing shape.

Commit messages and code in English. What the owner reads — pull requests, notes — in Russian.
The branch prefix for work the kit itself runs is `kit/`.

## Окружение

Ничего не ставится на хост: `uv`, Python и тесты живут в контейнере.

| Команда | Что делает |
|---|---|
| `make up` | собирает образ, поднимает контейнер, ставит зависимости (`uv sync`) |
| `make test` | `pytest` внутри контейнера |
| `make bench` | стенд: прогоняет подложенные ловушки и говорит, какие механизмы сработали |
| `make install-check` | доказательство S0: `uv tool install` кладёт рабочую команду на PATH |
| `make shell` | приглашение внутри контейнера |
| `PYTHONPATH=/projects/agent-kit/src python3 -m agent_kit …` | запуск на хосте, где живёт настоящий `claude` |
| `make down` | гасит, кэши остаются |
| `make clean` | гасит и сносит тома |

Портов проект пока не занимает — наружу ничего не смотрит. Порт понадобится демону (S7),
брать его тогда через `ports claim agent-kit`.

Секретов нет. Когда появятся — `~/.local/state/agent-kit/secrets`, режим 600, не в git.

## Где что лежит

| Место | Владелец |
|---|---|
| `src/agent_kit/` | сам кит |
| `~/.config/agent-kit/config.toml` | выбор этой машины: аккаунты, модели, роли |
| `~/.local/state/agent-kit/` | что истинно прямо сейчас: логи, база демона |
| `<проект>/.agent-kit/v3/project.toml` | что проект объявляет о себе: команды, ветка, роли; лежит в git |
| `<проект>/.agent-kit/v3/runs/<slug>/run.json` | состояние прогона; пишет только программа |
| `<проект>/docs/knowledge/` | знание проекта — владельца; кит только дописывает блоки шагом `record` |
| `bench/cases/<имя>/` | одна ловушка стенда: что подкладывается и что должно сработать |

`.agent-kit/runs/` — это вторая версия. Третья туда не смотрит и не пишет.

## Правила, которые уже действуют

- **Тест пишется первым, и это видно в истории.** Тесты идут своим коммитом — перед тем, который
  заставляет их проходить. Утверждать в сообщении коммита, что правило соблюдено, нельзя: это
  ровно то, что план называет «утверждение вместо следа».
- **Состояние двигается только через программу.** Ни один агент не редактирует `run.json`.
- **Отказ называет причину.** У каждой ошибки есть код (`no-step-running`, `bad-field: status`),
  и код выхода означает одно и только одно — см. `src/agent_kit/errors.py`.
- **Поле без читателя не пишется.** Правило 5 из плана. `splittable` и `blocking` больше
  не исключения: у первого читатель — драйвер, который продолжает шаг, у второго — шаг
  доставки, который отказывает.
- **Шаг исполняет либо сессия, либо программа.** Программа — там, где ответ можно
  проверить, а не выслушать: `verify` сам гоняет команды проекта, `deliver` сам собирает
  ветку, коммит и pull request из уже записанного. Программа не провайдер: её никто не
  выбирает и не настраивает, и она не пишет себя в запись как модель.
- **Шаг может объявить `gate`** — поле своего же вывода, с `false` в котором прогон
  дальше не идёт. Сам шаг при этом прошёл: записать правду — и была его работа.
- **Pull request — отчёт владельцу.** Открыто три вещи: что сделано, что нужно от
  владельца, что мешает выпуску. Остальное — под спойлером.
- **Читать — не инструкция.** Всё, что шагу нужно прочесть, драйвер вкладывает во вход
  (`driver/compose.py`). Пропустить нечего, значит и проверять нечего.
- **Метод — проза в `method/`**, не пакет. Едет внутри wheel (`force-include` в `pyproject.toml`),
  проверяется целью `make install-check`.
- **Провайдера по имени не называет никто вне `providers/`.** Реестр читает папку: есть
  `provider.toml` — есть провайдер. Что верно про инструмент — в `provider.toml`; что выбрала
  эта машина — в `~/.config/agent-kit/config.toml`; ни один файл не держит чужое.
- **Уровень провайдера меряется, а не объявляется:** `agent-kit provider check <имя>` проходит
  лестницу и называет ступень, на которой споткнулся.
- **Формат знания — тот же, что у второй версии.** Блок это цитата markdown, первая строка
  которой называет вид, дату и прогон. Кит добавил ровно один сегмент — `id: k7f3q2`, — и он
  такого же вида, как `pr: 29`, который в этом формате был всегда. Ни одна старая строка не
  переписывается, мигрировать нечего.
- **Идентификатор блока выводится, а не бросается жребием.** Из имени прогона и слов самого
  допущения. Поэтому ловушка стенда может назвать его заранее, а вторая попытка переписывает
  свой блок, а не кладёт рядом второй.
- **Дорогое допущение должно знанию блок.** Спрашивается дважды: проект, у которого знание
  есть, делает контракт шага `design` строже — отказ стоит одной сессии и называет поле; и
  ещё раз в `record`, что переживает прогон, собранный из других шагов. Проект без знания не
  должен ничего и выдумывать его не заставляют.
- **В знание пишет программа, а не сессия.** Модель возвращает поля, шаг `record` пишет файл
  и даёт блоку имя. Ни один агент не редактирует `docs/knowledge/` руками.
- **Вид блока без писателя не заводится.** Кит пишет только `assumed`: `frame` — это пакет
  (S8), `found` — ревью, чьи находки в знание пока не идут, `stale` — тот, кто заметил.
  `accepted` выброшен: шаблон, блок и правило закрытия, и ни одного писателя за всю жизнь
  проекта.
- **Годится ли работа к сдаче — спрашивается до того, как что-то записано.** Блокирующая
  находка, красные тесты, недоделанная сборка: `programs/deliverable.py`, и первым спрашивает
  `record`, а не `deliver`. Знание владельца не трогают ради работы, которая не выйдет.
- **Заявление проверяется стендом.** `make bench` — девятнадцать ловушек, каждая делает свой
  репозиторий и сносит его. Меняешь механизм — сначала посмотри, какая ловушка про него, и
  сломай её нарочно: если не сработала ровно одна, ловушка меряет не то. Стенд ничего не стоит
  (отвечает `providers/fake/`, а не живая модель) и потому гоняется на каждое изменение.
- **Ловушка доказывает, что она стояла.** Судья, который сверяет «ничего не случилось»,
  зелёный и там, где ловушки не было вовсе. Сначала он показывает, что ловушка сработала
  (файл не пуст, ветка была до прогона), и только потом судит.
- **Случай сверяет код отказа, а не английскую фразу.** Прозу перепишут, и случай станет
  мерить предложение. Нет кода у отказа — заведи код, а не подстроку.
- **Стенд подчиняется правилам кита.** Код 6 — механизм не сработал, код 7 — сам стенд не
  смог ответить; окружение случая — белый список, а не чёрный; всё, что стенд запускает,
  умирает вместе со своей группой процессов.
- **Провалившийся прогон не возобновляется молча.** `failed` — конечное состояние, причина
  остаётся в записи. Отказ одной попытки (`refuse_step`) и провал шага (`fail_step`) — разные
  события, и слова у них разные.
