# 2.28.0 — the project says what it checks itself for

One block to add to `project.yml`, and one thing that starts refusing to start.

An `epic` now stops at its gate until every kind of verification the kit knows about has an answer
here. Everything else — `ship`, `fix`, `sprint`, `next` — names what is unanswered in one line and
carries on building.

## The block

```yaml
verification:
  mutation: no 2026-08-20 — no runner installed for this ecosystem yet
  visual: no 2026-08-20 — nothing compares screens here
  contract: no 2026-08-20 — every outside call goes through a stand-in
  static_analysis: no 2026-08-20 — Pint formats, nothing analyses
  architecture: no 2026-08-20 — no written rules about structure yet
  performance: no 2026-08-20 — no path where slowness would be a defect
  accessibility: no 2026-08-20 — deferred until the interface settles
  security: no 2026-08-20 — nothing reachable by anybody but the owner

checks:
  verification_reviewed: 2026-08-20
```

**Five kinds you do not write here at all.** `suite`, `lint`, `types`, `end_to_end` and `mutation`
are read from `commands.test` / `lint` / `types` / `e2e` / `mutate`, which you already have — one
fact, one home. Write a line here for one of those five only to *refuse* it, since `commands` has
nowhere to put a reason.

**The list of kinds is not yours to keep.** It lives in `verification.yml` inside the plugin, with
what each one catches and which session runs it. A kind added there starts being asked of your
project on its next check; you never copy the list into the manifest, only the answers.

**An answer is a command or a dated refusal.** A command is checked for starting, like every other
command in that file — `yes` would be a claim nothing can test. A refusal carries a date because
*there is no front end* stops being true the week there is one, and the check asks again after six
months, or as soon as a dependency manifest moves under the answers.

`/agent-kit:blueprint` writes this block with you, and it is the only command that may. It reads the
repository rather than the description while it does — measured on two live projects, the cheapest
finding both times was an instrument already installed, already configured, and named nowhere: one
line here, and every run afterwards starts using it.

## What starts being asked of a feature

A finished `ship` or `fix` now carries `verified` in its run file: one record per kind whose `runs`
is `feature` and which this project answered with a command.

```json
"verified": [
  { "kind": "suite", "command": "make test", "result": "green, 118 passed" },
  { "kind": "lint", "command": "…/pint --test", "result": "green" },
  { "kind": "visual", "why": "this feature touches no screen" }
]
```

`why` instead of a result where the kind could not apply. A kind left out entirely is the finding —
it reads exactly like a kind that passed, which is the whole reason the project was asked in the
first place.

## What was removed

`commands.visual`, `commands.contract` and the `tests.visual` / `tests.contract` verdicts of 2.27.0,
along with `checks.sight_reviewed`. They were two kinds hard-wired into the template; they are now
two rows of a list that lives in the kit. If you filled them in during the day 2.27.0 was out, move
the commands into `verification` under the same names and delete the old keys.
